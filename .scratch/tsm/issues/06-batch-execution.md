# T-batch — 批量删除/归档执行

Type: grilling
Status: resolved
Blocked by: 02

## Question

这是你最初的核心痛点:多选后一次性删掉。定清执行模型:

1. **确认强度(已定方向)**:单删 = 快速 `y` 确认;批删 = 弹窗列出将删的标题 + 数量,按一个**明确键**(非回车,防误触)确认。归档/取消归档因可逆,是否免确认?本 ticket 敲定确认弹窗的确切内容与确认键。
2. **并发模型**:并发调用 `traex delete --force`。上限多少(吊在 R2 的并发安全结论)?用线程池 / async(tokio)?rust 侧如何 spawn 子进程并收集结果。
3. **进度反馈**:批量过程中 TUI 如何显示进度(N/总数、逐条打勾/打叉)?是否阻塞界面还是后台跑可继续浏览。
4. **部分失败**:某几条 `traex delete` 失败(退出码非 0)如何上报 —— 汇总面板列出失败项 + 原因?失败项是否留在列表里保持选中以便重试。
5. **完成后刷新**:删除/归档后如何重新查库刷新列表(整表重查还是移除已成功行);与 WAL 只读(R1)的关系。
6. **归档批量**:批量归档/取消归档是否复用同一执行框架。

## Answer

经 `/grilling` 三轮(用户 2026-08-08 逐条采纳),定清 tsm v1 的批量执行模型。承 R2(变更命令事实)与 T-layout(`selected: HashSet<SessionId>`、mutation 后重查库)。

### 1. 执行形态 —— 阻塞进度模态(非后台)

v1 批量删/归档跑起来时**阻塞在一个进度模态**,删完才放行继续浏览。理由:(a) 核心痛点是「多选→一次性删掉」这个聚焦动作,阻塞式心智最简;(b) R2 实测单条 ~0.08–2.0s、并发 4,一批通常 ~2s、最坏几十条约十几秒,模态内进度条 + `Esc` 取消足够;(c) 后台跑会引入真实竞态(光标停在正被删的行、一批未完又起第二批、列表眼皮下重排)。**边删边浏览的后台模式推 v2。**

### 2. 统一批处理引擎

一个 `BatchJob { op: Delete | Archive | Unarchive, ids: Vec<SessionId> }` 驱动同一条 spawn/进度/失败/刷新流水线。三个 op 的差异**只有三处**:确认门(§3)、lifecycle 门控(R2:只对活跃行 archive、只对归档行 unarchive)、`--force` 仅加在 delete 上。一套代码路径。

### 3. 确认强度(**revise 原 Question §1「单删=快速 `y`」**)

- **删除(不可逆 + 连带删 rollout `.jsonl`/`.artifacts`,R2)**:弹确认模态,列出**将删的标题**(>10 条则「前 10 条 + 还有 M 条」)+ 数量 + 「不可逆、同时删除磁盘文件」警告,用大写 **`D`** 确认(非 `Enter`,防误触,与 T-layout 键位表一致),`Esc`/`n` 取消。
- **单删(无选中、只删光标行)统一走同一模态**(只列 1 条)。**这里 revise 了 Question 里「单删=`y`」的原方向**:删除既不可逆又连带删磁盘文件,单键 `y` 恰是模态要防的误触,统一更安全一致。
- **归档 / 取消归档(可逆)= 免确认,即时执行**,按 R2 lifecycle 门控。

### 4. 并发 fan-out 机制

**`std::thread` 定长池(4)+ `mpsc` channel**,每个 worker 用 `std::process::Command` 跑 `traex <op> <uuid>`(delete 带 `--force`,R2),收集**退出码 + stderr 行**。**不用 tokio**:这是 fan-out 外部进程而非进程内异步 I/O,async 运行时零收益、徒增复杂度。池大小 = 4(R2 建议上限;硬编码,是否可配吊 T-pkg「默认配置」迷雾)。

### 5. 进度 UI

模态**顶部一行**:`Deleting… 12/30` + 进度条;下面一行**聚合计数** `✓ 20  ✗ 1  ⟳ 4`(成功/失败/在飞)。**不逐行渲染全部条目**(并发 4 乱序完成 + CJK 宽度抖动会成噪声)。失败项累积到模态底部小列表(带 R2 的 `Error: <msg>` 行)。归档/取消归档同套,动词换 `Archiving…`。

### 6. 部分失败上报 + 重试

跑完有失败 → 模态**转结果面**列出失败项 + 每条 stderr(R2 已是 `Error:` 前缀的人类可读行);全成功 → **自动关闭**(可选一行短 toast `Deleted 30.`)。**失败项保持选中,成功项移除**(承 T-layout「`selected` 按 id 过滤掉消失/变动行」)。结果面提示「按 `d` 重试失败项 / `Esc` 关闭」,重试 = 拿仍选中的失败集再走一遍同一流水线,零额外机制。

### 7. 刷新时机

收尾**全量重查库一次**(单个短只读事务,R1),**不做逐条增量移除**。理由:(a) 阻塞期间列表不可见,增量移除零收益;(b) archive 改 `rollout_path` 且移文件(R2),全量重查才反映权威真相、也自然处理「归档后从 active 视图消失」;(c) 避开中途重排与秒/毫秒 skew。重查后按 §6 过滤 `selected`。

### 8. 取消(`Esc`)语义

`Esc` = **停止派发新任务,不 kill 已在飞的 ≤4 个**(traex 删到一半被 SIGKILL 有留残状态风险,而单条最坏才 ~2s,R2),让在飞的自然收尾。随后进结果面:**已成功**去选,**已失败 + 未发起(cancelled)**一并保持选中可重试。即「取消」只保证不再多删,已发出的听天由命——对不可逆操作这是最安全的语义。

### 对 spec / 键位表的落地约束

- `d` = 有选中删全部选中、否则删光标行 → 确认模态(`D` 确认);`a` = archive/unarchive 按 lifecycle 门控、免确认(承 T-layout 键位表,本 ticket 定稿其确认语义)。
- `App.mode` 增补批处理态:`ConfirmDelete{ids}` → `Running{job, done, failed}` → `Result{failed}`(承 T-layout `Mode` 草案)。
- 批量**只涵盖 delete/archive/unarchive**;改名不入批(T-rename 已定 `r` 恒作用光标行、批量改名排除)。
